# tg-mcp — Telegram support gateway MCP server

## Overview

Customers report issues in Telegram groups instead of the ticketing system. `tg-mcp` is a
pull-mode gateway: a Bot API bot silently logs allowlisted customer groups into SQLite, and a
remote MCP server (streamable HTTP, bearer auth) lets Claude Code / Claude Desktop triage —
read new messages, reconstruct threads, search history, fetch attachments, and reply as the bot.

Deliberately out of scope: Forgejo integration. The harness (fj CLI / forge-issues skill) files
tickets; the only contract between tg-mcp and the harness is the **customer slug**. Tools never
expose raw chat IDs.

Accepted Bot API constraints:
- no history backfill — logging starts when the bot joins a group
- deletions are never delivered — no soft-delete tracking
- forum topics: partially supported — `message_thread_id` is stored and scopes thread
  reconstruction; replies inherit the topic from the replied-to message; a bare send (no
  `reply_to`) lands in General
- cloud Bot API caps `getFile` at 20 MB; the self-hosted `telegram-bot-api` server raises it to 2 GB

## Solution Overview

One process, three components composed in `run()`:

1. **Ingest loop** (`pkg/ingest`) — Bot API `getUpdates` long polling. Accepts `message` and
   `edited_message` only from allowlisted chats; everything else dropped and logged. Detects
   @mentions of the bot via entities. Offset committed only after the batch is stored, so a
   crash redelivers instead of losing messages; inserts are idempotent.
2. **Store** (`pkg/store`) — SQLite (WAL, `modernc.org/sqlite`, no CGO) + lazy file cache on
   one data dir. Standalone FTS5 table for search, maintained in Go transactionally.
3. **MCP server** (`pkg/server`) — streamable HTTP at `/mcp` via the official
   `modelcontextprotocol/go-sdk`, static bearer token checked with constant-time compare,
   `/ping` health endpoint, authenticated `/files/` download endpoint for large attachments.
   TLS is the reverse proxy's job.

Key design decisions:

- **Minimal in-house Bot API client** (`pkg/telegram`) instead of a bot framework. We need six
  endpoints (`getMe`, `getUpdates`, `deleteWebhook`, `sendMessage`, `getFile`, file download);
  a framework would own the update offset internally and fight our commit-after-store semantics.
- **Allowlist is the single source of truth both directions**: ingest filter and `send_reply`
  target validation both resolve through the same chat map.
- **Server stays dumb**: tools return raw messages, never summaries — intelligence lives in Claude.
- **No persisted getUpdates offset by design**: Telegram retains unconfirmed updates ~24h;
  redelivery after restart is the crash-safety mechanism. Do not add an offsets table.

Revisions after plan review (the why behind non-obvious choices below):

- **Outgoing replies are persisted**: Bot API does not echo the bot's own messages back through
  `getUpdates`, so `send_reply` upserts the `Message` returned by `sendMessage`. Without this,
  threads lose their answers and reply-chains to bot messages dangle.
- **`message_id` is per-chat**, so every message-addressed tool takes an optional `label` to
  disambiguate multi-group customers (same ambiguity-error pattern as `send_reply`).
- **FTS5 is standalone, not external-content**: composite-PK tables have unstable rowids and
  `INSERT OR REPLACE` skips delete-triggers, silently corrupting an external-content index on
  edits. A standalone FTS table updated in the same Go transaction avoids both for the cost of
  duplicated text (corpus is tiny).
- **Large files are served, not path-returned**: the MCP client is remote; a server-side path is
  useless to it. `get_file` returns an authenticated download URL on the same listener.

## Technical Details

### Configuration

Flags/env via go-flags (`long`, `env`, `default`, `description` tags):

| flag | env | purpose |
|---|---|---|
| `--telegram.token` | `TELEGRAM_TOKEN` | bot token |
| `--telegram.api-url` | `TELEGRAM_API_URL` | Bot API base, default `https://api.telegram.org` |
| `--telegram.local` | `TELEGRAM_LOCAL` | API server runs with `--local` (getFile returns filesystem paths) |
| `--auth-token` | `AUTH_TOKEN` | MCP bearer token |
| `--listen` | `LISTEN` | HTTP listen address, default `:8080` |
| `--data` | `DATA_DIR` | data dir (SQLite + files), default `./data` |
| `--chats` | `CHATS_FILE` | chat map file, default `chats.yml` |
| `--dbg` | `DEBUG` | debug logging |

`--telegram.local` is an explicit flag rather than path probing: a missing shared volume must
fail loudly, not fall through to a confusing HTTP 404.

Chat map is structured data, not flag persistence, so YAML rather than INI:

```yaml
chats:
  -1001234567890:
    customer: acme
    label: main        # optional, needed only when a customer has several groups
  -1009876543210:
    customer: globex
```

Validation at load: non-empty slugs, labels unique per customer. Types are exported
(`Config`, `ChatInfo`) — consumed by ingest and server.

### Data model (SQLite, WAL)

```sql
CREATE TABLE messages (
  id           INTEGER PRIMARY KEY,       -- surrogate, stable rowid for FTS
  chat_id      INTEGER NOT NULL,
  message_id   INTEGER NOT NULL,
  thread_id    INTEGER,                   -- message_thread_id (forum topics), NULL otherwise
  sent         TEXT    NOT NULL,          -- RFC3339 UTC
  sender_id    INTEGER NOT NULL DEFAULT 0,  -- 0 when from is absent (anonymous admin, channel)
  sender_name  TEXT    NOT NULL,          -- falls back to sender_chat title or 'unknown'
  from_bot     INTEGER NOT NULL DEFAULT 0,  -- 1 for our own sent replies
  reply_to     INTEGER,
  text         TEXT    NOT NULL DEFAULT '', -- message text OR media caption
  is_mention   INTEGER NOT NULL DEFAULT 0,
  edited_at    TEXT,
  media_type   TEXT,                      -- photo|document|video|voice|... or NULL
  file_id      TEXT,
  file_unique_id TEXT,
  file_name    TEXT,
  file_size    INTEGER,
  UNIQUE (chat_id, message_id)
);
CREATE INDEX idx_messages_chat_sent     ON messages(chat_id, sent);
CREATE INDEX idx_messages_chat_reply_to ON messages(chat_id, reply_to);
CREATE TABLE chats   (chat_id INTEGER PRIMARY KEY, customer TEXT NOT NULL, label TEXT NOT NULL DEFAULT '');
CREATE TABLE cursors (chat_id INTEGER PRIMARY KEY, last_triaged_message_id INTEGER NOT NULL);
CREATE VIRTUAL TABLE messages_fts USING fts5(text);  -- standalone; rowid = messages.id
```

- upsert via `INSERT ... ON CONFLICT(chat_id, message_id) DO UPDATE` (never `INSERT OR REPLACE` —
  it changes the surrogate id and skips triggers); edits keep original `sent`, set `edited_at`
- FTS maintained explicitly in Go in the same transaction as the message write
  (delete old FTS row + insert new on edit); no SQL triggers
- `text` holds the caption for media messages; `caption_entities` are checked for mentions
- a reply to one of the bot's own messages sets `is_mention` (addressing the bot without @)
- `chats` refreshed from config at startup (config wins; rows for removed chats stay for history)
- file cache: `files/<file_unique_id>/<file_name>` under data dir, populated lazily
- ingest batch is written in a single transaction; offset advances only after commit

### Thread reconstruction (`get_thread`)

Walk `reply_to` chain up from the given message to its root, collect the closure of messages
referencing any chain member, then **span-fill**: return every message in the chat between the
chain's first and last timestamp, padded ±5 minutes. When the anchor message has a `thread_id`,
span-fill is scoped to that topic. Chain defines the span; span-fill catches answers typed
without hitting "reply". Result capped (500 messages) with a `truncated` flag.

### MCP tools (8)

All take/return customer slugs; chat IDs stay internal. Every tool that addresses a message
(`get_thread`, `get_file`, `mark_handled`, `send_reply` with `reply_to`) accepts optional
`label` and fails with the list of labels when the customer has several groups and neither
`label` nor an unambiguous context pins one. Message listings include `label` for multi-group
customers.

| tool | params | notes |
|---|---|---|
| `list_customers` | — | customers, their group labels, unread counts |
| `list_new` | `customer?, limit?` | messages above cursor (default limit 100): sender, time, snippet, mention/media flags |
| `get_thread` | `customer, message_id, label?` | full ordered messages, span-fill algorithm, capped + `truncated` flag |
| `get_history` | `customer, from?, to?, limit?, label?, cursor?` | chronological bulk; defaults last 24h, limit 200; a full page returns `next_cursor`, pass it back as `cursor` for the page before it (➕ replaced the planned `to`-based paging, see Task 5) |
| `search` | `query, customer?, from?, to?, limit?` | FTS5 + LIKE fallback, snippets + ids |
| `get_file` | `customer, message_id, label?` | images inline (MCP image content), text-ish as text, large binaries → authenticated download URL + metadata |
| `send_reply` | `customer, text, reply_to?, label?` | plain text (no parse_mode), >4096 chars rejected with "split it" error; persists the sent message; audit-logged |
| `mark_handled` | `customer, message_id, label?` | advances the chat cursor |

### File retrieval

- `getFile` response handling by explicit mode: `--telegram.local` → `file_path` is an absolute
  path on a shared volume, copy into cache; otherwise → download
  `GET {api-url}/file/bot{token}/{file_path}` into cache
- cloud mode: `getFile` fails for files >20 MB — surface a clear error naming the limit
- small files (images, text) returned inline in the tool result under a size threshold;
  larger files: cached, tool returns `GET /files/<file_unique_id>` URL on the same listener,
  protected by the same bearer token (fetchable with curl)

### Error handling

- Bot API envelope (`ok`/`error_code`/`description`/`parameters`) parsed once at the request
  layer; 429 `retry_after` honored with a single retry for **all** methods, then surfaced
- long-poll: dedicated `http.Client` with timeout = poll timeout + 10s; retry with exponential
  backoff (cap ~30s) on transient errors; **409 Conflict (webhook set) fails fast** with a clear
  message — `deleteWebhook` is called at startup
- poison updates: batch retried 3 times on store failure, then failing updates are logged at
  error level with full payload and skipped — one bad update must not stall all chats
- `migrate_to_chat_id` service message logged prominently with old → new ID (allowlist needs
  a manual `chats.yml` update)
- service messages (joins, pins, etc. — no text, no media) are filtered out at ingest
- MCP auth failures: 401 with `WWW-Authenticate: Bearer`, no other detail;
  `crypto/subtle.ConstantTimeCompare`
- structured logs (`log/slog`) to stdout: ids-only for stored messages, full audit line for
  every send
